# 风险与改进建议

## 1. 当前风险

### 1.1 业务逻辑依赖硬编码文本

识别逻辑强依赖 `text.txt` 中一定存在 `RK3288`，并且目标内容一定在下一行。

问题：

- 一旦 OCR 格式变化，整条链路会失效
- 如果后续识别对象不再是 `RK3288`，逻辑必须改代码

### 1.2 `vendor/model` 校验存在交互缺陷

`start_detection()` 一开始就执行：

```python
vendor_editable.set(0)
toggle_vendor_model()
```

这会在每次检测开始时关闭“编辑前三码/后四码”。随后代码又要求：

```python
if not sn or (vendor_editable.get() == 1 and (not vendor or not model)):
```

结果是：

- 如果用户本来想手工输入 `vendor/model`，按钮一按就被禁用
- 逻辑上几乎不可能在本次检测中继续保持“需要人工输入”的状态

这部分像是交互设计或状态管理上的 bug。

### 1.3 CSV 并发和覆盖风险

流程是“下载整个 CSV -> 本地追加 -> 整个文件重新上传”。如果多台设备同时操作，会有：

- 后写覆盖前写
- 记录丢失
- 文件竞争

`results.csv` 目前不像可靠存储，更像临时共享文件。

### 1.4 错误处理不完整

例子：

- `text.txt` 不存在时，日志里引用了 `e.stderr`，但该分支里未必存在 `e`
- `ossutil` 失败只反馈 PASS/FAIL，没有区分下载失败、上传失败、认证失败
- `cv2.VideoCapture(device)` 打开失败没有更细的诊断信息

### 1.5 路径与环境强耦合

大量使用相对路径，导致：

- 启动目录必须正确
- 不方便做 systemd、桌面快捷方式、容器化封装

### 1.6 缺少依赖声明与启动文档

当前目录没有：

- `requirements.txt`
- `README.md`
- 部署说明
- 版本信息

交接成本会偏高。

## 2. 优先级最高的改进

### P0

- 修复 `vendor_editable` 在检测开始时被强制重置的问题
- 把路径改成基于 `__file__` 的绝对路径
- 为 `ossutil`、OCR 执行失败、`text.txt` 缺失补齐明确错误信息

### P1

- 把 `RK3288` 与解析规则提取成配置项
- 为 `results.csv` 写入增加基本锁或改为服务端接口
- 增加 `requirements.txt` 和根目录 `README.md`

### P2

- 将 OCR 二进制的输入/输出约定文档化
- 把 GUI、业务逻辑、存储逻辑拆分成独立模块
- 增加日志文件而不是只显示在 UI 文本框中

## 3. 如果要继续接手这个项目，建议先做什么

1. 先在真实目标设备上确认 `main.py` 能稳定跑通。
2. 用几组真实样本验证 `text.txt` 的格式是否始终稳定。
3. 修复 `vendor/model` 交互状态问题。
4. 补一份最小可运行文档和依赖文件。
5. 再考虑重构，而不是直接大改 OCR 链路。
